# Архитектура

## Решение

Не форкаем ни один из существующих проектов. Greenmask и Presidio — внешние зависимости
(Docker-образ и pip-пакеты соответственно). Свой код пишем только там, где готового решения нет:
детекция → конфиг Greenmask, offline-генерация правдоподобных замен через LLM, сервис,
отдающий Greenmask готовые значения по запросу.

## Альтернативы и компромиссы

### Движок дампа/трансформации: Greenmask vs postgresql_anonymizer vs Tonic Fabricate

| Вариант | Почему отклонён / почему выбран |
|---|---|
| **`postgresql_anonymizer`** (Dalibo) | Декларативный подход "правила маскирования в самой схеме БД" (DDL-комментарии/`SECURITY LABEL`). Плюс — маскирование становится частью модели данных, пишется разработчиками схемы. Минус, критичный для нас: требует установки расширения (`CREATE EXTENSION anon`) **в целевую БД**, часто с суперпользовательскими правами на этапе инициализации — то есть работает *внутри* прод-инстанса, а не как отдельный потоковый пайплайн поверх дампа. Детекция PII (`anon.detect()`) — статическая, по имени колонки, без анализа содержимого. Для задания, где нужен **отдельный сервис**, не трогающий прод-БД напрямую, и **детекция по содержимому** (не только по имени), это не подходит как основной движок — но сама идея "человек подтверждает список масок" у нас переиспользована в `detector/out/report.md` (auto-applied vs review-only).|
| **Tonic Fabricate / Tonic.ai** | Коммерческая closed-source SaaS-платформа синтетических данных с ML-генерацией, широким набором коннекторов и UI из коробки. Отклонена по требованию задания «максимально переиспользовать существующие **open-source** компоненты, поверх готового агентского фреймворка» — Tonic не open-source и не встраивается как библиотека/образ в свой пайплайн, это отдельный внешний продукт с лицензированием. Дополнительно — vendor lock-in и невозможность прогнать демо без платной подписки, что противоречит требованию воспроизводимого демо-прогона в репозитории.|
| **Greenmask (выбран)** | Open-source, Docker-образ, потоковый `pg_dump`/`pg_restore`-совместимый протокол — работает поверх дампа/копии, не требует расширений в проде. Готовая интроспекция схемы, referential integrity, параллелизм из коробки. Расширяется собственным `Cmd`-трансформером без форка. Минусы, с которыми пришлось работать: собственный hash-engine слабее для консистентности между параллельными воркерами (см. ниже), а `custom_transformers`-регистрация недокументирована (см. §1 и `Cmd` vs `custom_transformers` ниже).|

### Consistency-движок: встроенный hash-engine Greenmask vs собственный mapping store

Greenmask имеет встроенный `hash`-трансформер (детерминированная замена на основе хеша от
значения) — казалось бы, закрывает требование "сквозные замены" без всякого своего кода.
Отклонён как основной механизм по двум причинам:

1. **Формат замены не контролируется на уровне сохранения распределения категории** —
   хеш даёт детерминированный, но не обязательно *правдоподобный* результат (это ближе к
   псевдонимизации по хешу, чем к LLM-генерации реалистичных значений, требуемой заданием).
2. **Уникальность и коллизии — открытая проблема самого Greenmask** (задокументированная
   в их issue-трекере), а у нас есть возможность дедуплицировать на этапе `generator`,
   до того как значения попадут в дамп, а не полагаться на хеш-функцию постфактум.

Взамен — собственный mapping store (Redis) с предзаполнением до старта дампа (см. §4
ниже). Компромисс: дополнительный внешний сервис и предварительный offline-этап генерации
вместо "бесплатной" консистентности хеша — но взамен получаем контролируемое качество
замен и предсказуемую стоимость LLM-вызовов (батчами по категории, не по строке).

### Точка встраивания в Greenmask: `custom_transformers` vs `Cmd`

См. §1 ниже — `custom_transformers` предпочтительнее по эргономике (именованный,
многократно используемый трансформер под командой 200 человек), но недокументирован в
части декларации параметров; `Cmd` выбран как рабочее решение с тем же рантайм-контрактом
(персистентный процесс, JSON stdin/stdout), возможность мигрировать на
`custom_transformers` позже не требует переписывания `lookup-service`.

## Компоненты

```
┌──────────────┐     ┌───────────────┐     ┌──────────────────┐     ┌───────────┐
│   detector   │ →  │   generator   │ →  │   mapping store   │ ←  │  greenmask │
│  (Presidio,  │     │  (LangGraph,  │     │ (Redis/Postgres,  │     │ (внешняя   │
│   наш код)   │     │   наш код)    │     │  наш код)         │     │  зависим.) │
└──────────────┘     └───────────────┘     └──────────────────┘     └───────────┘
                                                      ↑
                                              ┌───────────────┐
                                              │ lookup-service│  ← custom_transformers (Cmd, stdin/stdout)
                                              │  (наш код)    │
                                              └───────────────┘
```

### 1. Greenmask — внешняя зависимость (Docker-образ, не форк)

Закрывает: интроспекцию схемы Postgres, потоковый dump/restore, сохранение объёма строк и
referential integrity, параллельный дамп (`-j/--jobs`).

Точка расширения — встроенный `Cmd`-трансформер: персистентный процесс, построчно читающий
stdin и пишущий stdout (JSON driver), а не спавн процесса на каждое значение. Изначально
планировали регистрировать `lookup-service` через `custom_transformers` (именованный
трансформер, доступный через `greenmask list-transformers`) — на практике эта секция требует
самостоятельной YAML-декларации каждого параметра (включая правильно типизированный
`columns`), без наследования от схемы встроенного `Cmd`, и нигде в репозитории не
задокументирована/не приведена примером. Отложили как отдельное улучшение (полезно для
единой регистрации под именем для команды 200 человек), сейчас `Cmd` конфигурируется
напрямую per-table в `detector/detect.py`.

Многоколоночные зависимости (email должен соответствовать сгенерированным имени/фамилии)
на реальной схеме Adventure Works оказались **межтабличными**, а не внутристрочными:
имя лежит в `person.person`, email — в `person.emailaddress`, связаны по
`businessentityid`. `TemplateRecord` эту зависимость не закрывает (он оперирует одной
строкой одной таблицы), поэтому вместо него используются identity-бандлы в mapping
store, ключованные по `businessentityid` — см. §4 и `lookup-service/app/main.py`.

### 2. detector/ — наш код + Presidio (pip-зависимость)

Presidio (`presidio-analyzer`, `presidio-structured`) прогоняется на **сэмпле строк** каждой
таблицы (не на всей таблице) → отчёт "колонка → категория PII". На выходе — фрагмент
`custom_transformers`/`transformation` конфига Greenmask, назначающий `lookup-service` на
обнаруженные колонки. Соединяет два независимых мира (детекция по значениям + потоковый
движок), которые нигде готовыми не связаны — наш архитектурный вклад.

### 3. generator/ — наш код (LangGraph)

Offline-этап, отдельный от дампа. Для каждой обнаруженной категории:
1. Профилирование колонки на сэмпле (распределение значений, для категориальных —
   частоты категорий).
2. Батч-запрос к LLM с этими метриками в промпте (probability-driven prompting,
   см. arXiv:2505.02659) — LLM возвращает пул правдоподобных значений, сохраняющих
   распределение оригинала, а не единичное значение на вызов.
3. Валидация (формат, дедупликация) и запись в mapping store.

LLM вызывается пакетно на категорию, не на каждую строку — иначе не проходит по
производительности при больших объёмах.

### 4. mapping store — наш код, Redis или Postgres-таблица

Ключ — `HMAC(salt, original_value)` → значение замены. **Обязательно внешнее хранилище**,
не память процесса: Greenmask поддерживает параллельный дамп (`-j`), значит несколько
экземпляров `lookup-service` могут работать одновременно на разных таблицах. In-memory
маппинг в этом случае даст разным воркерам разные замены для одного и того же исходного
значения — требование сквозных замен тихо сломается. Внешнее хранилище также даёт
воспроизводимость между прогонами (важно при регулярной эксплуатации командой ~200 человек).

### 5. lookup-service — наш код

Персистентный процесс, зарегистрированный в Greenmask как `custom_transformer`. Читает
JSON-строки из stdin (значение + контекст колонки), ищет в mapping store по хешу,
отдаёт готовую замену через stdout. Если промаха нет в сторе на момент дампа — это ошибка
конфигурации пайплайна (generator должен был отработать заранее), а не повод генерировать
на лету.

**JSON-контракт между Greenmask и lookup-service фиксируется первым же шагом** — это
единственная граница между чужим Go и нашим Python, от неё зависит всё остальное.

## Что сознательно не делаем

- Не трогаем PK/FK, если это surrogate keys (стандартная рекомендация из документации
  postgresql_anonymizer) — тогда referential integrity сохраняется автоматически.
- Не реализуем оркестрацию LLM-агентов с нуля — используем LangGraph.
- Не пытаемся гарантировать уникальность через один только hash-engine Greenmask — это
  открытая проблема у них самих; дедупликация — на уровне mapping store.
