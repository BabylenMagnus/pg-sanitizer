# db-sanitization

Санитизация (обезличивание) PostgreSQL-баз: правдоподобные, сгенерированные LLM замены
чувствительных значений, с сохранением схемы, referential integrity, объёма строк и
разнообразия данных. Проверено end-to-end на дампе Adventure Works.

Полное обоснование архитектурных решений — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Формат решения

Задание допускает сдачу либо репозиторием с инструкцией по запуску, либо развёрнутым
стендом. Сдаём **оба варианта одновременно**, не потому что нужно было выбрать одно, а
потому что они закрывают разные части задания дёшево, без дублирования кода:

- **Этот репозиторий** — воспроизводимый пайплайн санитизации (см. «Запуск» ниже):
  `docker compose run` без интерактивного ввода, без секретов в коде, полностью
  проверяемый локально с нуля на Adventure Works.
- **Развёрнутый стенд** — [sanitaizer.cheesy-pizza.ru](https://www.sanitaizer.cheesy-pizza.ru)
  (отдельный репозиторий `sanitaizer-web`, Next.js): живой дашборд с реальным прогоном
  этого пайплайна — «до/после» по образцам строк (`/samples`), отчёт по найденным PII
  (`/report`), метрики верификации — referential integrity, объём строк, разнообразие
  (`/metrics`), сырые логи каждого шага (`/logs`). Плюс `/jobs` — self-service запуск
  новых прогонов пайплайна через веб (роль admin может подключить произвольную внешнюю
  Postgres-базу или загрузить дамп), поверх той же jobs-обвязки, что описана в
  [`api/README.md`](api/README.md).

Обоснование: сам по себе репозиторий с `docker compose run` не даёт того наглядного
«сопоставления до/после, подтверждающего обезличивание данных при сохранении связей,
объёма и разнообразия», о котором просит задание в разделе «Результат» — таблицы в
терминале это формально показывают, но неудобно ревьюить. Стенд даёт то же самое
сопоставление в виде страницы, которую можно открыть и сравнить визуально, без
необходимости поднимать пайплайн локально. Репозиторий при этом остаётся источником
истины — стенд ничего не делает такого, что нельзя было бы прогнать этими же командами
локально.

## Безопасность: куда физически пишутся данные

Коротко: **исходную базу пайплайн никогда не изменяет — ни при каком типе источника.**
Санитизированная копия всегда создаётся в нашей собственной `playground-db`, никогда на
сервере, откуда пришли данные.

- `detector/` и `generator/` открывают соединение к исходной базе в режиме
  `set_session(readonly=True)` — Postgres физически не даст выполнить запись даже при
  ошибке в коде.
- `greenmask dump` — это `pg_dump`, он читает исходную базу потоково и не пишет в неё.
- Все операции записи (`DROP DATABASE`/`CREATE DATABASE`, `greenmask restore`) выполняются
  только против **target**-соединения источника, которое всегда указывает на нашу
  `playground-db` — независимо от того, откуда взят source (встроенная демо-база, внешний
  DSN или загруженный дамп). Для внешнего DSN-источника `source` (откуда читаем) и
  `target` (куда пишем санитизированную копию) — это два разных Postgres-сервера с двумя
  разными наборами credentials в `connection`-конфиге источника (`api/app/main.py::
  create_dsn_source`); они никогда не смешиваются (см. `api/README.md`, раздел
  «Source vs. target»).

## Почему PostgreSQL

Из трёх вариантов задания (MySQL/PostgreSQL/MSSQL) выбран PostgreSQL, потому что для него
существует наиболее зрелый open-source инструмент потокового dump/transform/restore —
[Greenmask](https://github.com/GreenmaskIO/greenmask) — с готовой интроспекцией схемы через
`pg_catalog`, поддержкой параллельного дампа и рекурсивным subsetting'ом по FK. Строить
такой движок с нуля значило бы игнорировать требование задания «максимально переиспользовать
готовые компоненты».

## Из чего состоит

| Компонент | Роль | Наш код? |
|---|---|---|
| [Greenmask](https://github.com/GreenmaskIO/greenmask) | Интроспекция схемы, потоковый dump/restore, referential integrity, параллелизм (`-j`) | Нет — Docker-образ `greenmask/greenmask:latest`, не форк |
| [Presidio](https://github.com/data-privacy-stack/presidio) (`presidio-analyzer`) | Детекция PII по содержимому (NER + regex + checksum-распознаватели) | Нет — pip-зависимость |
| [LangGraph](https://github.com/langchain-ai/langgraph) | Оркестрация offline-пайплайна генерации замен | Нет — pip-зависимость |
| `detector/` | Presidio-анализ сэмпла строк → отчёт PII → фрагмент конфига Greenmask | Да |
| `generator/` | LangGraph-граф: профиль распределения → батч к LLM/Faker → mapping store | Да |
| `lookup-service/` | Персистентный процесс, встроенный в Greenmask как `Cmd`-трансформер, отдающий готовые замены из Redis | Да |
| Redis (`mapping-store`) | Внешнее консистентное хранилище `оригинал → замена` | Нет — образ `redis:7-alpine` |

Свой код — только там, где связки между готовыми инструментами не существует: детекция
не знает про Greenmask, Greenmask не знает про LLM, а мы это соединяем.

## Как устроена замена значений

### Коротко, в двух словах

Пайплайн проходит по базе в три шага, и на каждом шаге "участвует" разный инструмент —
это важно не путать:

1. **Берём и проверяем** — по каждой колонке каждой таблицы смотрим небольшой кусок
   значений (до 200 строк) и решаем: это персональные данные (имя, email, телефон,
   номер карты...) или нет. Решение принимает **Presidio** — это не LLM, а модель
   распознавания сущностей (NER), она просто размечает "похоже на email"/"похоже на
   имя". Colonки-идентификаторы (PK/FK, справочные коды) в проверку вообще не попадают —
   они по построению не могут быть свободным PII-текстом. Результат этого шага — список
   "какая колонка что содержит", а не список данных для замены.
2. **Придумываем замены** — для каждой колонки, помеченной как PII, просим **LLM**
   (или Faker, если ключа LLM нет) сгенерировать нужное количество новых правдоподобных
   значений того же типа ("придумай 500 email-адресов"). В LLM реальные значения не
   передаются вообще — только тип и количество. Замены складываются в общее хранилище
   (Redis) заранее, до начала следующего шага.
3. **Синтезируем — по всей таблице, без выборки.** На этом шаге сэмплирования уже нет:
   `greenmask dump` потоково читает **каждую строку каждой колонки**, помеченной как PII
   на шаге 1, и для каждого значения берёт готовую замену из хранилища (шаг 2). Один и
   тот же реальный email/имя всегда получает одну и ту же замену — так связи между
   таблицами (например, между именем и email в разных таблицах) не ломаются. Всё, что не
   помечено как PII, копируется как есть.

Иными словами: лимит в 200 строк существует только на шаге 1 (понять тип колонки) —
сама подмена данных на шаге 3 всегда идёт по полному объёму таблицы.

### 1. Обнаружение (`detector/`)

Presidio анализирует **реальные значения** (сэмпл до 200 строк на колонку), а не только
имена колонок — это отличает подход от `postgresql_anonymizer`'s `anon.detect()`, статического
словаря по имени колонки. Presidio здесь — NER-модель, не LLM: она классифицирует тип
содержимого (имя/email/телефон/...), не генерирует текст. На Adventure Works нашлось 35 кандидатов на первом прогоне;
у lightweight-модели `en_core_web_sm` заметная доля ложных срабатываний на коротких
ALLCAPS-кодах (`currencycode`, `countryregioncode` — распознавались как `ORGANIZATION`).
Добавлены фильтры:
- колонки, участвующие в PK/FK, исключаются — это справочные коды по построению, а не
  свободный PII-текст;
- deny-list по подстрокам имени (`code`, `type`, `category`, `flag`, `group`);
- минимальный размер непустой выборки.

Оставшийся шум не отбрасывается молча: находки с шумными категориями (`ORGANIZATION`,
`DATE_TIME`, `NRP`) остаются в `detector/out/report.md` для **ручного ревью**, но не
попадают автоматически в конфиг Greenmask (`auto_applied: false`) — то же разделение
"детектор предлагает, человек подтверждает", что рекомендуют сами Presidio и
`postgresql_anonymizer` в документации. Итог на Adventure Works: 18 находок, 12
auto-applied (10 таблиц) / 6 review-only.

### 1.5. Определение языка исходных данных

Каждой находке `detector/` присваивает `language` ("ru"/"en") — по мажоритарному Unicode-
скрипту символов в сэмпле (доля кириллических vs латинских букв), а не статистическим
детектором вроде `langdetect`: тот рассчитан на связный текст и ненадёжен на коротких
PII-значениях (имена, ID) — прямая проверка диапазона символов и проще, и точнее для этой
задачи. У чисто цифровых "документных" колонок (телефон, SSN/СНИЛС-подобный ID) в значениях
нет ни одной буквы — язык такой колонки наследуется от других PII-колонок той же таблицы
(двухпроходная агрегация в `detector/detect.py::main()`), а не молча считается английским.
Язык управляет локалью Faker/LLM-промптом в `generator/` — русские имена получают русские
замены, английские — английские, без смешения скриптов внутри одной записи. Проверено
отдельным скриптом `generator/test_language_backend.py` (синтетические EN/RU сэмплы,
включая цифровые колонки без буквенного сигнала) — Adventure Works целиком на английском,
поэтому в реальном прогоне ветка "ru" не задействуется.

### 2. Генерация правдоподобных значений (`generator/`, LangGraph + LLM)

Offline-этап, **до** запуска дампа, не во время него. Граф:
`load_report → generate_plain → generate_identities → persist`.

Для каждой auto-applied колонки: достаём реальные различные значения из Postgres (никогда
не покидают процесс генератора), просим LLM (или Faker в offline-режиме) о таком же
количестве **новых** правдоподобных значений данной категории, строим биективное
соответствие «оригинал → замена» и пишем в Redis по ключу `HMAC-SHA256(salt, оригинал)`.

**Приватность промпта**: в LLM никогда не уходят реальные значения — только
`(entity_type, сколько значений нужно)`. Соответствие с реальными данными строится
локально. Побочный эффект такого дизайна: раз одно исходное значение всегда даёт одну и
ту же замену, частотное распределение категории (сколько раз какое значение встречается)
сохраняется автоматически, без необходимости раскрывать модели реальные частоты —
практическая реализация идеи из
[arXiv:2505.02659](https://arxiv.org/abs/2505.02659) (probability-aware генерация
табличных данных) без утечки самих данных.

LLM подключается через `langchain_openai.ChatOpenAI` (`OPENAI_API_KEY`/`OPENAI_MODEL`).
Без ключа пайплайн не падает — использует локальный Faker-бэкенд с тем же интерфейсом
(`generate(entity_type, count)`), чтобы задание можно было прогнать полностью
воспроизводимо без секретов. Кап на число различных значений на колонку
(`GENERATOR_MAX_DISTINCT_PER_COLUMN`) ограничивает стоимость/задержку LLM-вызовов; при
Faker-бэкенде (локальный, бесплатный) кап поднимается на порядок автоматически, чтобы не
терять разнообразие там, где это ничего не стоит.

### 3. Многоколоночные/межтабличные зависимости (identity-бандлы)

На реальной схеме Adventure Works зависимость «email должен соответствовать
имени/фамилии» — межтабличная: имя в `person.person`, email — в `person.emailaddress`,
связаны по `businessentityid`. Greenmask'овский `TemplateRecord` для этого не подходит
(он работает в рамках одной строки одной таблицы), поэтому реализован свой механизм:
`businessentityid` прокидывается в `lookup-service` как контекст (не изменяется), и для
него в Redis лежит согласованно сгенерированный бандл `identity:<id>` (имя + производный
email), который читают обе таблицы. Проверено: `Elizabeth Dorsey` →
`elizabeth.dorsey@example.test` идентично в обеих таблицах.

### 4. Консистентность и параллелизм (`lookup-service` + Redis)

Ключевое архитектурное решение: mapping store **полностью предзаполняется** генератором
до старта дампа. Во время `greenmask dump -j 4` каждый `Cmd`-процесс (свой на таблицу)
только читает уже существующие ключи — никакой гонки записи между конкурентными
воркерами разных таблиц. Если значение всё-таки не найдено (детектор/генератор что-то
упустили), срабатывает защитный fallback: детерминированный плейсхолдер на основе того
же `HMAC(salt, значение)`, безопасный при гонке, потому что не зависит от того, какой
воркер его вычислил.

Все финальные значения — из кэша, из LLM/Faker, из fallback — обрезаются по фактической
длине целевой колонки (`information_schema.columns.character_maximum_length`), которую
`lookup-service` подгружает при старте — без этого `pg_restore` падал бы на узких
`varchar(N)`-колонках (например `accountnumber varchar(15)`, `passwordsalt varchar(10)`
в Adventure Works).

## Масштабируемость и переиспользуемость

- **Объём данных**: Greenmask сам по себе потоковый (`pg_dump`/`pg_restore`-совместимый
  протокол, не грузит таблицу целиком в память) и поддерживает параллельный дамп (`-j`).
  Наш код не читает данные построчно в Python вне этого потока — `lookup-service`
  обрабатывает построчный JSON-стрим, не буферизует таблицу.
- **LLM как отдельная стадия, не узкое место дампа**: генерация происходит один раз,
  offline, батчами по категории (а не по строке) — стоимость и время генерации не растут
  с объёмом строк, а с числом *различных* значений в колонке, которое почти всегда на
  порядки меньше числа строк.
- **Регулярная эксплуатация командой ~200 человек**: детекция и генерация — идемпотентные,
  воспроизводимые шаги (тот же salt + тот же образ → тот же результат), которые можно
  прогонять по расписанию отдельно от дампа; `report.md` даёт человеку явную точку
  контроля перед тем, как что-то автоматически замаскируется.
  - **Ни одного ручного шага внутри пайплайна.** Все 5 команд в разделе «Запуск» —
    `docker compose run/exec`, без интерактивного ввода, без правки конфигов руками между
    шагами (конфиг Greenmask собирается автоматически из `config.template.yml` +
    сгенерированного детектором `transformation.detected.yml`). Единственное, что задаётся
    человеком — `.env` (соль и, опционально, ключ LLM) один раз при первой настройке
    источника, не при каждом прогоне.
  - **Готово к встраиванию в CI/cron без переписывания.** Каждый шаг — самостоятельный
    `docker compose run --rm <service>` с кодом возврата, который CI/раннер интерпретирует
    как обычно (0/ненулевой). Ничего не рассчитано на интерактивный терминал.
    Детекцию и генерацию можно гонять по расписанию отдельно от dump/restore (например,
    еженедельно пересобирать mapping store, а dump — по требованию), потому что
    generator полностью предзаполняет mapping store заранее и не зависит по времени от
    момента запуска dump.
  - **Один пайплайн — много источников.** `docker-compose.yml`/`.env` не хардкодят
    конкретную БД: подключение, соль и модель — параметры окружения. Для команды 200
    человек это означает, что один и тот же Docker-образ обслуживает разные
    БД/окружения, различающиеся только `.env`, без форка репозитория под каждую базу —
    именно это (а не отдельный веб-фронтенд с job-очередью, что выходит за рамки этого
    задания) и есть архитектурное свойство "рассчитано на регулярную эксплуатацию
    большой командой", которое здесь запрашивается.
  - **Человеческая точка контроля не блокирует automation.** `report.md`/`report.json`
    разделяют находки на `auto_applied` (идут в automation без участия человека) и
    review-only (требуют явного решения) — это значит, что задание "прогонять
    регулярно без участия человека" и задание "ничего не замаскировать по ошибке"
    не противоречат друг другу: пайплайн можно поставить в cron целиком, а review-only
    находки просто накапливаются в отчёте для периодического ревью, не останавливая
    автоматические прогоны.
- **Расширяемость на другие форматы**: детектор и генератор оперируют абстракцией
  "колонка → сэмпл значений → категория → замена", не завязанной на Postgres-специфику
  за пределами `detector/detect.py`/`generator/generate.py` (SQL-запросы к
  `information_schema`). Добавление источника данных другого типа (например, дампа CSV/
  документов) требует нового адаптера, отдающего тот же контракт "колонка → сэмпл", а не
  переписывания detector/generator/lookup-service.

## Запуск

```bash
cp .env.example .env   # задать свой MAPPING_SALT; опционально OPENAI_API_KEY/OPENAI_MODEL

docker compose build detector generator greenmask

# 1. поднять исходные данные (Adventure Works в original + пустая transformed)
docker compose run --rm playground-dbs-filler

# 2. обнаружить PII
docker compose run --rm detector

# 3. offline-генерация замен (LLM при наличии OPENAI_API_KEY, иначе Faker-фолбэк)
docker compose run --rm generator

# 3.5. transformed должна быть пустой перед restore (создаётся playground-dbs-filler,
#      но если прогоняете повторно — пересоздайте, иначе pg_restore выдаст безвредные,
#      но шумные "already exists" по объектам схемы)
docker compose exec playground-db psql -U postgres -c "DROP DATABASE IF EXISTS transformed;"
docker compose exec playground-db psql -U postgres -c "CREATE DATABASE transformed;"

# 4. дамп исходной БД с анонимизацией на лету
docker compose run --rm greenmask dump --config=/var/lib/greenmask/config.generated.yml

# 5. восстановление в transformed
docker compose run --rm greenmask restore --config=/var/lib/greenmask/config.generated.yml latest
```

`docker compose run greenmask ...` сам поднимает свои зависимости (`detector`,
`generator`, `mapping-store`, `playground-dbs-filler`) через `depends_on`, шаги 2-3 выше
можно опустить при первом запуске — они приведены отдельно, чтобы было видно
промежуточные артефакты (`detector/out/report.md`, логи generator).

После этого `original` (порт `54316`, БД `original`) и `transformed` (та же БД-инстанция,
БД `transformed`) содержат одинаковое число строк по каждой таблице, с обезличенными
PII-колонками (см. `detector/out/report.md` за списком) и сохранённой связностью между
`person.person`/`person.emailaddress` по имени/email.

## Тестовые данные

Adventure Works (`github.com/morenoh149/postgresDBSamples`) — тот же набор, что в
официальном playground Greenmask: готовая схема со связями (FK), разными типами данных,
достаточным объёмом для проверки целостности и разнообразия. ~20 000 строк в основных
таблицах (`person.person`, `sales.customer`), FK-графы глубиной в несколько уровней
(`sales.salesorderdetail → salesorderheader → customer → person`).

## Известные ограничения

- Presidio на `en_core_web_sm` даёт разумный, но не идеальный recall/precision — часть
  находок сознательно оставлена только для ручного ревью (см. detector/detect.py,
  `AUTO_APPLY_ENTITY_TYPES`), а не подмешивается в автоматику вслепую.
- Кап на число различных значений на колонку при LLM-бэкенде (по умолчанию 500) — значения
  сверх капа получают defensive-фолбэк вместо LLM-сгенерированного значения.
  Это осознанный компромисс cost/latency vs полнота, снимается либо повышением капа, либо
  батчированием генерации по частям (архитектурных ограничений для этого нет).
- Identity-бандлы сейчас реализованы только для связки `person.person`
  `firstname/middlename/lastname` ↔ `person.emailaddress.emailaddress` по
  `businessentityid` — механизм общий (любая таблица с этим FK и нужными колонками
  подхватится автоматически детектором), но других таких связок в детектируемых PII-
  колонках Adventure Works не нашлось.
